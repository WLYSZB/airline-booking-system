## 2. 业务规则与领域层

### BUG-01 中转时间反例测试数据算错

- 类型：测试缺陷，不是产品缺陷。
- 现象：单元测试 `rejectsConnectionBelowAirportMinimum` 失败，期望结果为空，实际返回了一个联程行程。
- 复现：
  - 前段到达时间为 `base + 60min`。
  - 测试里后段起飞写成 `base + 130min`。
  - 计算得到中转时间 `70min`，大于机场最小中转 `60min`，产品允许该行程是正确的。
- 根因：写测试时没有从“到达时刻 + 最小中转时间”反推后段起飞时刻，凭感觉填了 130 分钟。
- 修复：把后段起飞改为 `base + 90min`，实际中转时间变成 `30min`，测试通过。
- 验证：`mvn test` 中 4 个领域测试全部通过。
- 报告可写角度：
  - 边界值分析：等于最小中转时间应允许，小于才拒绝。
  - 测试失败不等于产品失败，必须先核对测试输入。
- 状态：已修复。

### BUG-02 票价未乘乘客人数

- 类型：业务缺陷。
- 现象：查询条件为 2 人时，跨航司行程展示和收据金额为 `850.00`，正确金额应为 `1700.00`。
- 复现：
  - 航段票价之和为 `390 + 460 = 850`。
  - 2 人预订后仍返回 `850.00`。
- 根因：
  1. `TripComposer` 只对单乘客票价求和。
  2. `BookingCoordinator` 生成收据时也只累计一次票价。
  3. V2 中央登记计算总额时同样漏乘人数。
  三个位置都复制了“票价求和”逻辑，修正时容易漏层。
- 修复：
  - `domain-core/.../TripComposer.java`：先乘 `passengers`，再应用 `OwnDiscount`。
  - `domain-core/.../BookingCoordinator.java`：收据总价乘乘客人数。
  - `central-server/.../BookingService.java`：V2 权威登记同样乘人数。
  - 单元测试中的预期金额从 900/1000 改为 1800/3000。
- 验证：
  - 真实库 V1：`B2102 → A1104`，2 人，预订金额 `1700.00`。
  - 真实库 V2：Java 客户端同样登记 `1700.00`。
- 报告可写角度：
  - 业务规则必须只有一份权威实现。
  - 同一规则在 V1 服务端和 V2 客户端复用时，金额计算容易漏掉人数维度。
- 状态：已修复。

### BUG-03 H2 与 Oracle 布尔字段不兼容

- 类型：环境/跨库设计问题。
- 现象：设计初期中央库 H2 使用 `BOOLEAN` 存 `same_airline_discount`，迁移到 Oracle 时 `BOOLEAN` 不是表字段类型。
- 根因：H2 与 Oracle 对 SQL 类型和 JDBC 布尔映射支持不同；按单一数据库写 DDL 会埋下迁移问题。
- 修复：
  - 中央表字段改为 `INT`/`NUMBER(1)`。
  - Java 写入时用 `1/0`，读取时 `rs.getInt(...) == 1`。
  - MySQL/Oracle 两套 DDL 都按整数定义。
- 验证：真实 MySQL 中央库读写通过；Oracle 航司表不使用该字段，但 Oracle 航司的其余字段和事务正常。
- 报告可写角度：
  - 跨数据库方言设计，不要把开发库特性当成通用 SQL。
- 状态：已修复。

## 3. 航司服务与数据库

### BUG-04 联表查询同名列歧义

- 类型：环境/构建，实际会发展成运行时缺陷。
- 现象：航司 A 启动后，定时释放过期预占任务报错：
  `Ambiguous column name "FLIGHT_INSTANCE_ID"`。
- 复现：`flight_hold` 与 `flight_instance` 都有 `flight_instance_id`，查询 `SELECT flight_instance_id ... JOIN ...` 没加表别名。
- 根因：联表查询中 `flight_instance_id`、`status`、`passengers` 等同名列未加表别名。
- 修复：所有联表查询列显式写成 `h.hold_id`、`h.flight_instance_id`、`h.passengers`、`h.status`、`f.fare`；`status` 在明细查询中别名为 `hold_status`。
- 验证：重启航司服务后定时任务不再报错；V1/V2 预占、取消、过期释放正常。
- 报告可写角度：
  - SQL 别名规范和数据库可移植性。
  - 启动成功不代表后台定时任务正常，必须查运行日志。
- 状态：已修复。

### BUG-05 Oracle 重复建表触发 ORA-00955

- 类型：环境/构建。
- 现象：启用 Oracle schema 初始化时启动失败：
  `ORA-00955: 名称已由现有对象使用`。
- 根因：Oracle 表已存在，而启动参数强制执行 `CREATE TABLE`；Oracle 没有 MySQL 的 `CREATE TABLE IF NOT EXISTS` 等价写法。
- 修复：
  - Oracle 默认 `spring.sql.init.mode=never`。
  - 空 Oracle 库首次启动才设置 `ORACLE_SCHEMA_INIT=true`，第二次启动去掉。
  - 启动脚本把该选择显式化，避免每次启动重复执行 DDL。
- 验证：航司 C 连接现有 Oracle 表启动成功，查询、预占、扣座、取消均通过。
- 报告可写角度：
  - Oracle/MySQL 初始化策略差异。
  - 初始化脚本应区分“首次建库”和“日常启动”。
- 状态：已绕过并固化。
- 遗留：没有从空 Oracle schema 完整重跑一次 DDL，属于后续要补的验证。

### BUG-06 Oracle 航司 C 的名称和折扣是旧配置

- 类型：业务数据问题。
- 现象：Oracle 航司 C 的航班返回 `airlineName=楚天航空`、`ownDiscountPercent=10`，而配置应为“长江航空 12%”。搜索按 10% 展示、收据可能按 12% 计算，存在金额解释不一致。
- 根因：早期启动时用了默认航司名称和折扣写入 Oracle；之后的 `FlightSeeder` 只在表为空时插入，不修正已有行。
- 修复：
  - `FlightSeeder` 在表非空时执行配置校正：
    `UPDATE flight_instance SET airline_name=?, own_discount=? WHERE airline_code=?`。
  - 仅修正展示名称和折扣，不动座位、价格、航班时刻等业务数据。
- 验证：重启后 C 航司所有航班返回“长江航空 / 12%”。
- 报告可写角度：
  - 配置是唯一事实源，种子数据要支持幂等校正。
  - 数据迁移不能只看“有数据就跳过”。
- 状态：已修复。

### BUG-07 中央登记曾信任客户端票价

- 类型：安全/设计问题。
- 现象：初版 V2 的 `/api/bookings/register` 请求体包含客户端生成的航段、票价和总价，中央服务直接保存。恶意客户端可以伪造低价收据。
- 根因：把厚客户端当成可信数据源，没有回到航司服务读取权威预订明细。
- 修复：
  - `RegisterBookingRequest` 缩减为 `bookingReference + passengers`（座位偏好随乘客携带）。
  - 新增航司接口 `GET /reservations/{ref}/details`，返回航段、票价、乘客数和状态。
  - 中央服务逐个航司查询，确认所有航段 `CONFIRMED` 且乘客数一致，再用权威票价重新计算总价。
  - 客户端伪造的 `totalPrice` 不再被接受。
- 验证：V2 真实库登记返回 `1700.00`，与航司权威票价一致。
- 报告可写角度：
  - 厚客户端的安全信任边界。
  - ATAM 中的 security 质量属性：客户端执行业务逻辑，但权威数据必须由服务端复核。
- 状态：已修复。

## 4. 一致性与状态

### BUG-08 中央登记失败后航司占座未释放

- 类型：一致性问题（Saga 补偿缺口）。
- 现象：测试结束后，航司 B2102 / A1104 各少了 2 个座位，但中央库没有对应的有效订单。
- 复现背景：一次 V2 运行在“航司已确认、中央登记请求构造”阶段抛出 `NoSuchMethodError`，流程中断，没有进入取消逻辑。
- 根因：
  - 客户端先完成航司预占/确认，再调用中央登记。
  - 中央登记抛异常时，客户端没有对已确认的航司预订做补偿取消。
- 修复：
  - `ThickBookingService.book()` 对 `centralClient.register()` 增加 catch。
  - 登记失败立即调用 `BookingCoordinator.cancel(...)` 逆序取消航司预订。
  - 错误信息带出预订编号和补偿结果。
- 验证：修复后 V2 正常登记和取消；演示库重置后座位从 `[4,6]` 正常回到 `[4,6]`。
- 报告可写角度：
  - 跨独立数据库的 Saga/补偿不是全局 ACID。
  - “航司已确认、中央未登记”是最危险的中间态。
- 状态：同步异常路径已修复。

### BUG-09 取消后收据航段状态仍是 CONFIRMED

- 类型：一致性问题/展示问题。
- 现象：订单状态已变为 `CANCELLED`，但收据里的每个航段仍显示 `CONFIRMED`。
- 根因：`BookingRepository.updateStatus()` 只更新了 `central_booking.status`，没有同步 `booking_leg.status`。
- 修复：当订单状态改为 `CANCELLED` 时，同时执行
  `UPDATE booking_leg SET status='CANCELLED' WHERE booking_reference=?`。
- 验证：V1 取消返回的航段状态为 `['CANCELLED', 'CANCELLED']`。
- 报告可写角度：
  - 聚合根状态和子实体状态的一致性。
  - 收据是审计材料，不能出现自相矛盾。
- 状态：已修复。

### BUG-10 B 服务默认连到了 airline_a

- 类型：环境/配置问题。
- 现象：真实库联调时跨航司查询结果为空；直接请求航司 B 的接口，返回的却是 A 航司的航班和中文名。
- 根因：MySQL profile 的默认 URL 和用户名都是 `airline_a`。手动启动 B 时没有传 `--spring.datasource.url/username`，于是 B 进程读的是 A 库。
- 修复：
  - 删除 MySQL/Oracle profile 中数据库 URL、用户名、密码的默认值。
  - 启动脚本为 A/B 分别显式传 `airline_a` / `airline_b` 和各自账号。
  - 配置缺失时启动失败，而不是静默连错库。
- 验证：B 接口只返回 `B` 航司数据；跨航司 `BB2102 → AA1104` 查询恢复。
- 报告可写角度：
  - 配置默认值的危险性。
  - “启动成功”不等于“连接正确”。
- 状态：已修复。

## 5. 构建与运行环境

### BUG-11 Maven 执行到旧版 RegisterBookingRequest

- 类型：依赖/构建问题。
- 现象：V2 冒烟报：
  `NoSuchMethodError: RegisterBookingRequest.<init>(String, List, SeatPreference)`。
- 根因：`mvn -pl thick-client exec:java` 从本地 Maven 仓库解析 `domain-model`，而仓库里还是旧的 6 参数版本；源码虽然改了，但没 `install` 到本地仓库。
- 修复：
  - 运行厚客户端前先执行
    `mvn -f pom.xml -pl thick-client -am install -DskipTests`。
  - `run-thick-client.sh` 和 `run-thick-smoke.sh` 固化这一步。
- 验证：V2 冒烟输出 `THICK_CLIENT_SMOKE_PASS`。
- 报告可写角度：
  - Maven reactor 编译和本地仓库运行时的差异。
  - 可复现运行脚本的必要性。
- 状态：已修复。

### BUG-12 Windows 下运行中的 jar 锁定构建

- 类型：环境/构建。
- 现象：`mvn clean package` 在 `airline-server` 阶段失败，无法删除或重命名 jar。
- 根因：Windows 文件锁，正在运行的 Java 进程持有 `target/*.jar`。
- 处理：先按端口定位项目 Java 进程并停止，再构建；不能直接删除被占用文件。
- 验证：停止服务后 `mvn clean package` 成功。
- 报告可写角度：
  - 构建生命周期应与运行实例隔离。
  - CI 中每次用独立工作目录，避免本地锁。
- 状态：已处理。

### BUG-13 Git Bash 的 `/d/...` 路径 Spring 读不到

- 类型：环境/脚本问题。
- 现象：`start-real-db.sh` 启动 A/B/Central 时执行 schema 失败：
  `No schema scripts found at location 'file:/d/软件/.../schema-*.sql'`。
- 根因：Git Bash 的 `pwd` 是 MSYS 路径 `/d/...`；Spring 的 `file:` URL 在 Windows JVM 下需要 `D:/...`。
- 修复：脚本用 `cygpath -m "$ROOT"` 转换成 `D:/...`，拼成
  `file:D:/.../schema-*.sql`。
- 验证：A/B/Central 建表成功，航司 C（无 schema 初始化）也正常启动。
- 报告可写角度：
  - Shell 路径和 JVM 路径不是同一套规则。
  - 脚本要显式处理 Windows/MSYS 差异。
- 状态：已修复。

### BUG-14 curl 被代理导致健康检查假成功

- 类型：环境/脚本问题。
- 现象：服务已经停止，脚本里的健康检查仍表现成功；终端输出
  `upstream connect failed: 由于目标计算机积极拒绝...`，但 shell 判断为成功。
- 根因：当前终端环境有 HTTP 代理，`curl localhost` 被代理接管，返回了代理错误文本而不是连接失败状态。
- 修复：脚本健康检查加 `--noproxy '*'`，强制绕过代理。
- 验证：关闭服务时返回连接失败，启动后返回 `200`。
- 报告可写角度：
  - 测试工具的环境副作用。
  - “健康检查通过”必须有可信的探测方式。
- 状态：已修复。

### BUG-15 `$!` 不是 Windows PID，停止脚本失效

- 类型：环境/脚本问题。
- 现象：启动脚本写出的 PID 文件无法被 `kill -0` 识别，`stop-all.sh` 停不掉 Java 服务。
- 根因：Git Bash 的 `$!` 是 MSYS 进程号，不是 Windows 进程号；Windows 需要 `tasklist/taskkill`。
- 修复：
  - 用 `/usr/bin/ps -W` 查 `WINPID` 写 PID 文件。
  - 用 `tasklist //FI "PID eq ..."` 判活。
  - 用 `taskkill //PID ... //F` 停止。
  - 启动失败时 trap 清理已启动进程。
- 验证：`stop-all.sh` 正确停止四个服务，端口释放；重复启动时脚本能识别已有进程。
- 报告可写角度：
  - 跨平台脚本不能假设 Unix PID 语义。
  - 运维脚本也需要测试。
- 状态：已修复。

### BUG-16 只有注释的 SQL 文件被解析为空

- 类型：环境/脚本问题。
- 现象：为了跳过 Oracle 重复建表，创建了只有注释的 `empty-schema.sql`，Spring 报
  `IllegalArgumentException: 'script' must not be null or empty`。
- 根因：SQL 初始化器去掉注释后得到空脚本，不是合法 SQL。
- 修复：临时脚本改为 `SELECT 1 FROM DUAL;`；最终改为默认不执行 Oracle schema，并提供 `ORACLE_SCHEMA_INIT` 开关。
- 报告可写角度：
  - 运维脚本的边界条件。
  - “空”与“无操作”不是一回事。
- 状态：已修复。

### BUG-17 配置文件出现明文数据库密码

- 类型：安全/设计问题。
- 现象：`application-mysql.yml`、`application-oracle.yml` 中出现真实数据库密码默认值。
- 根因：为了快速联调直接把密码写进默认配置，违反“配置与密钥分离”。
- 修复：
  - 所有 profile 改为只读取 `AIRLINE_DB_PASSWORD`、`CENTRAL_DB_PASSWORD`。
  - 启动脚本隐藏输入密码或从环境变量读取。
  - 检查源码和构建出的 jar：`application-mysql.yml` 中只剩 `${...}` 占位符。
- 验证：源码扫描无真实密码；jar 内配置无真实密码。
- 报告可写角度：
  - 硬编码密钥的风险和最小权限账号。
  - 这一点可以直接放进 ATAM 的 security 讨论。
- 状态：已修复。

### BUG-19 JS 读取了未序列化的 Java 方法名

- 类型：UI/接口约定问题。
- 现象：前端模板使用 `trip.airlinesLabel` 和 `trip.direct`，实际 JSON 中没有这两个字段。
- 根因：`TripOffer` 的 `airlinesLabel()`、`direct()` 是普通 Java 方法，不是 Jackson 默认序列化的 record 组件；前端把它们当 JSON 属性使用。
- 修复：前端从 `trip.legs` 自行推导：
  `tripAirlines()` 去重航空公司代码，`trip.legs.length === 1` 判断直达。

- 报告可写角度：
  - 后端 DTO 和前端字段必须明确契约。
  - 不要依赖框架对方法的隐式序列化。
- 状态：已修复。

### BUG-20 favicon 缺失被全局异常处理成 500

- 类型：环境/错误处理问题。
- 现象：浏览器请求 `/favicon.ico`，中央服务日志出现
  `NoResourceFoundException` 并走 `500` 全局异常处理。
- 根因：静态资源未找到是 404 语义，但全局 catch-all 把它当成未知异常。
- 修复：
  - 增加 `/favicon.svg` 并在页面 `<link rel="icon">` 引用。
  - 异常处理器对 `NoResourceFoundException` 返回 404，不再打 500。
- 验证：`/favicon.svg` 返回 200，缺失资源返回 404，日志无 500。
- 报告可写角度：
  - 全局异常处理的边界，静态资源 404 和业务异常要区分。
- 状态：已修复。

## 8. 当前尚未解决或需要后续验证的风险

这些不是“已经修好的 bug”，不要写成已解决，后面做 ATAM 或复盘时可以继续补充：

1. **V2 进程崩溃窗口**：如果客户端在航司确认后、中央登记前直接崩溃（不是抛异常），同步补偿不会执行，仍可能留下已确认但未登记的航司预订。当前只有人工排查/后续补偿方案，没有自动恢复任务。
2. **V2 部分取消失败**：客户端失败时会登记 `CANCEL_PENDING`，中央后台任务会重试；如果航司长期不可用，仍会停留在待处理状态，需要人工介入。
3. **Oracle 空库建表未完整验证**：本轮 Oracle 表是已存在的，应用完成了读写和事务验证，但没有从空 schema 重跑全部 Oracle DDL。
4. **没有身份认证和授权**：当前是课程实验环境，未实现 JWT/SSO；ATAM 的 security 场景可以把它列为主要风险。
5. **单实例部署**：中央和航司都是单实例，没有高可用和故障转移；性能结论不能外推到生产规模。
6. **演示数据单日**：目前只种了 `2026-11-15` 的航班，其他日期为空，不能用于完整日期边界测试。
7. **GUI 自动化仍不完整**：已有 `ThickClientUiDemo` 启动界面、自动查询和截图，但没有覆盖弹窗提交、多乘客 GUI 全流程。

## 11. 2026-11-03 修复批次

- **预订校验**：`BookingCoordinator` 在预占前重新读取各航司权威航班，校验归属、航段连续、最短中转、人数一致和航班字段未过期；新增 4 个单元测试。
- **幂等**：新增 `booking_idempotency` 占位表和 SHA-256 请求指纹；同 key 重试复用稳定预订编号，同 key 改内容返回 `IDEMPOTENCY_CONFLICT`，并发同 key 返回 `IDEMPOTENCY_IN_PROGRESS`。
- **取消重试**：V2 部分取消会登记 `CANCEL_PENDING`；中央新增 30 秒后台重试任务，任务成功后收口为 `CANCELLED`。
- **过期确认**：航司确认 SQL 增加 `expires_at > now` 检查；0 分钟预占黑盒测试返回 `HOLD_EXPIRED`。
- **前端防护**：查询条件变化后禁止使用旧报价；预订幂等键在同一弹窗内复用；错误显示在弹窗内；空航司选择被拦截；查询和收据查询加超时/loading。
- **可访问性与移动端**：补 dialog `aria-labelledby`、输入框 `name/autocomplete`、弹窗最大高度和滚动、窄屏断点、`prefers-reduced-motion`。
- **测试与文档**：新增 CI workflow、`docs/real-database-setup.md`，账号模板统一为单密码。
